## Accepted parts

The interface-remediation design is accepted in principle and does not need to be redesigned:

- semantic task score is separated from strict interface-compliance metrics;
- mathematics extraction is deterministic and uses expected type/schema, not expected value, before scoring;
- conflicting normalized math candidates are rejected;
- coding extraction uses AST only and selects the first qualifying Python/unlabeled fenced block defining the requested top-level entrypoint;
- candidate source is not executed during extraction;
- strict interface metrics remain secondary diagnostics;
- adapter validation uses synthetic fixtures only and the committed 13 tests pass;
- candidate set, exact revisions, BF16/no-quantization policy, neutral Qwen envelope, generation policy, context envelope, execution host/GPU policy, coding judge policy, and Gate acceptance thresholds remain unchanged;
- no selected model was executed during A5R1 construction.

## Required change: structural freshness of the Math case set

The v1.2.0 mathematics set is not sufficiently fresh for this remediation experiment.

Exact prompt strings, constants, and answer values differ from v1.1, but a human audit found substantial near-isomorphic reuse of the v1.1 case structure. In particular, the opening v1.2 mathematics sequence closely mirrors the v1.1 sequence: linear equation, fractional-number word problem, ratio counters, arithmetic sequence, divisor count, urn probability, midpoint, exponent/inclusion-exclusion style tasks, often with only constants and wording changed.

This matters because v1.2 is being constructed **after v1.1 selected-model outputs were observed**. A fresh remediation benchmark should not preserve case skeletons whose model behavior is already known. Exact-string overlap alone is therefore an insufficient freshness criterion.

The software-coding sample reviewed shows materially different task instances and does not currently require replacement.

## Required v1.2.1 revision

Create a new benchmark version `gate-a-cross-skill-v1.2.1` rather than editing v1.2.0 in place.

Preserve v1.2.0 unchanged as a frozen, not-approved audit artifact.

For v1.2.1:

1. Keep the approved v1.2 semantic adapter, scoring contract, template, tokenizer policy, case counts, difficulty distribution, execution controls, and strict-interface metrics unless a genuine implementation bug is discovered.
2. Replace the 48 mathematics cases with structurally fresh instances, not merely new constants in v1.1 templates.
3. Concept/domain coverage may remain comparable, but avoid one-to-one positional correspondence with v1.1 cases and avoid near-isomorphic prompt/problem skeletons whose selected-model behavior has already been observed.
4. Prefer changed mathematical constructions or compositions within each broad skill family, e.g. different equation forms, different probability/combinatoric structures, different geometry constructions, different number-theory operations, and multi-step compositions rather than coefficient substitution.
5. Preserve the required 10 foundational / 24 intermediate / 14 advanced distribution.
6. Recompute all math oracles and token counts from the new cases.
7. Add a machine-readable/manual-audit freshness record that explicitly distinguishes:
   - exact prompt overlap;
   - exact oracle overlap;
   - exact constant overlap where practical;
   - structural/near-isomorphic overlap review.
8. Do not execute General, Math, or Coder checkpoints during this revision.
9. Do not calibrate difficulty or select cases from any selected-model result.

## Documentation correction required

The v1.2.0 manifest contains an inaccurate authoring statement saying the remediation was produced "without observing selected-model outputs." That is not true: the remediation was motivated by observed v1.1 outputs.

For v1.2.1, use precise wording such as:

> The remediation design was informed by the observed v1.1 interface confounder, but no selected-model raw response was used as an adapter fixture, no expected value was used to choose an extracted candidate, and no v1.2.1 case/oracle/difficulty label was selected or tuned using selected-model performance on that case.

Do not claim that selected-model outputs were never observed.
